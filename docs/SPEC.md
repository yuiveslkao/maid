# maid 仕様書

PC 上でいつでも音声で話せる、好みの声と性格のキャラクター兼調べものエージェント。完全に個人用。

## 1. 環境

| 項目 | 内容 |
|---|---|
| CPU | Core i7-11700F（8 コア 16 スレッド） |
| GPU | RTX 3060 Ti（**VRAM 8GB**） |
| RAM | 16GB |
| OS | Windows |
| 音声出力 | ヘッドホン（エコー対策は不要） |
| マイク | 本体の物理ミュートボタンを使う |

VRAM 8GB がいちばんの制約です。**GPU は LLM 専用**にして、音声認識と音声合成は CPU で動かすのが基本方針です。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 基盤 | Open-LLM-VTuber v1.2.1（本体は改造せず、外付けで拡張する） |
| 入力 | 音声とチャット |
| 待受 | 常時待受・ウェイクワードなし。ミュートは物理ボタン。マイクに声が入ったら（雑音は除く）すべて反応する |
| Discord | **Discord で通話中は自動で声に反応しない**（チャットは使える）。通話アプリは Discord だけを対象にする |
| 割り込み | キャラが話している途中で話しかけたら止まる |
| 応答速度 | 速いほど良い。目標は話し終わってから 1 秒未満 |
| 頭脳 | ローカル LLM（Ollama）。会話は外に出さない |
| 耳（音声認識） | SenseVoice（sherpa-onnx, CPU）。精度が足りなければ faster-whisper（GPU） |
| 声 | 当面は AivisSpeech。将来は好きな声優に近い声を学習したモデル |
| 検索 | 閲覧と検索だけ（ログイン・購入・フォーム送信はしない）。Chrome でなくてよい。メモリは節約しつつ精度も重視 |
| 回答の出し方 | 調べた結果はチャットに出す（出典 URL 付き）。声では短く要約 |
| 外に出してよいもの | **検索クエリと閲覧したページだけ** |
| 会話ログ | 自分の PC に保存（全文と要約）。それを使ってキャラが育っていく（Hermes Agent 的） |
| 見た目 | 当面なし |
| キャラから話しかける | 欲しい（内容は §6 の案から選ぶ） |
| 予定管理・長期記憶 | 欲しい（§7, §8） |
| 画面 | 簡単な GUI があればよい → Open-LLM-VTuber のデスクトップアプリをそのまま使う（§10） |

## 4. 全体構成

```
                    ┌──────────────── 自分の PC（外に出ない） ─────────────────┐
 マイク ─▶ VAD ─▶ 音声認識 ─▶ ┌────────────┐ ─▶ ブリッジ ─▶ AivisSpeech ─▶ ヘッドホン
 チャット ──────────────────▶ │ 頭脳 (Ollama)│
                             │  会話はここだけ │◀─▶ maid-core（MCP）: 記憶 / 予定 / 自発発話
                             └─────┬──────┘
                                   │ 「調べて」のときだけ
                                   ▼
                             maid-search（MCP）
                               ├ 検索クエリを作る（個人情報を除く）── ▶ 検索エンジン   ← 外に出る: クエリ
                               └ ページ取得・本文抽出 ─────────────── ▶ Web ページ     ← 外に出る: 閲覧
                    └──────────────────────────────────────────────┘
```

- 拡張機能は Open-LLM-VTuber の **MCP 連携**で外付けします（本体を改造しないので、本体のアップデートで壊れにくい）。
- `maid-core` と `maid-search` はこのリポジトリで作る予定の MCP サーバーです。
- 画面と本体の間には **Discord ゲート**（`gate/discord_gate.py`）を挟みます。Discord がマイクを使っている間（＝通話中）は、
  マイク音声とキャラからの自発発話の合図を本体に渡しません。判定は Windows のマイク使用記録（タスクバーのマイク表示と同じ情報）で行います。

### API の頭脳を使う場合

「会話は外に出さない」と「API を頭脳にする」は両立しません（API に会話全体を送ることになる）。代わりに:

- **会話はローカル LLM が担当**。
- **調べものの要約だけ API に任せてもよい**（オプション）。API に渡すのは「検索クエリ」と「取得したページ本文」だけで、会話履歴や記憶は渡さない。
  どちらも「外に出してよいもの」の範囲なので、方針どおりです。
- ローカル 8B クラスでも、検索結果を読んで要約する程度なら実用になります。精度が足りないと感じたときだけ有効にします。

## 5. 応答速度

話し終わってから声が出るまでの内訳と目標（ローカル・RTX 3060 Ti 想定の概算。実測は `bench_latency.py`）:

| 段階 | 初期設定 | 調整後の目標 | 調整方法 |
|---|---|---|---|
| 話し終わり判定（VAD） | 約 1.1 秒 | **0.4〜0.5 秒** | 画面の Redemption Frames を 35 → 12〜15 |
| 音声認識（SenseVoice, CPU） | 0.1〜0.2 秒 | 同左 | — |
| LLM が最初の一言（読点まで）を出す | 0.3〜0.6 秒 | 0.2〜0.4 秒 | 非 thinking モデル、短いシステムプロンプト、「最初の一文は短く」の指示、モデルを常駐（`keep_alive: -1`） |
| 最初の一言の音声合成 | 0.2〜0.5 秒（CPU） | 0.1〜0.3 秒 | 頭の無音を 0 にする（ブリッジで設定済み）、必要なら GPU |
| **合計** | **約 2 秒** | **約 1〜1.4 秒** | |

- 1 秒を切るには、さらに「相づちを先に返す」（後述の Phase 5）か、話し終わり判定をもっと攻めるしかありません。
- Open-LLM-VTuber は「最初の読点で読み上げを始める」機能（`faster_first_response`）があり、有効にしています。
- 検索するときは数秒かかるので、先に「ちょっと調べるね」と言ってから調べる動きにします（Phase 2）。

## 6. キャラから話しかける（自発発話）

Open-LLM-VTuber には「一定時間黙っていたら話しかける」機能があります（画面の設定で ON）。何を話すかの候補:

| 候補 | 内容 | 必要なもの |
|---|---|---|
| 予定のリマインド | 「15 時から○○だよ」 | 予定管理（§8）。時刻で話しかける仕組みが必要 |
| 朝のあいさつ | 今日の予定と前日の話題を一言 | 予定・記憶 |
| 前の話の続き | 「昨日言ってた○○どうなった？」 | 長期記憶（§7） |
| 休憩のすすめ | 長時間黙っているときに「そろそろ休憩しない？」 | なし（今すぐ可） |
| 雑談 | 好きな話題を振る | 記憶にある好み |
| 興味のある話題の新着 | 「○○の新情報出てたよ」 | 検索（クエリが外に出る）。ON/OFF 可能にする |

おすすめは「予定のリマインド」「前の話の続き」「休憩のすすめ」の 3 つから始めることです。

## 7. 記憶と成長（Hermes Agent 的）

すべて自分の PC の SQLite と Markdown ファイルに保存します（`%USERPROFILE%\maid-data\` 想定）。

| 層 | 中身 | いつ作る |
|---|---|---|
| 会話ログ | 全文（音声認識の結果とキャラの返事） | 毎ターン |
| セッション要約 | 1 回の会話ごとの要約・話題・約束ごと | 会話が一定時間止まったとき |
| ユーザープロフィール | 好み、生活リズム、呼ばれ方、NG など（`USER.md`） | 要約から更新 |
| キャラのメモ | キャラ自身の「覚えておきたいこと」「最近の関心」（`MEMORY.md`） | 要約から更新 |
| 振り返り | 1 日分を見直して、プロフィールとメモを整理・矛盾を直す | 夜間・PC が空いているとき |

- 会話のたびに、プロフィールとメモ（短く保つ）をシステムプロンプトに入れます。昔の話は必要なときだけ検索します（全文検索と、CPU で動く小さな埋め込みモデル）。
- 記憶を消す・直すコマンドを用意します（「それは忘れて」）。
- 8B クラスの LLM で要約・振り返りの質が足りるかは要検証です。足りなければ、夜間だけ大きめのモデルを CPU で動かす案があります（16GB RAM では 14B 程度が上限）。

## 8. 予定管理

- **ローカルの SQLite に保存**（Google カレンダー連携は予定が外に出るのでしない。必要なら .ics の書き出し・取り込みで対応）。
- 音声で「明日の 15 時に歯医者」と言えば登録、「今週の予定は？」で読み上げ。
- 時刻になったらキャラが話しかける。Open-LLM-VTuber の自発発話は「黙っている時間」でしか動かないので、**時刻で話しかける仕組みは追加で作る**必要があります（Phase 3 で設計）。代わりに Windows の通知を出す方法もあります。

## 9. 声

| 段階 | 方法 |
|---|---|
| 今 | AivisSpeech ＋ AivisHub の配布モデル（学習不要） |
| 本番 | 好みの声の音声を集めて学習する。AivisSpeech 用モデル（Style-Bert-VITS2 系）か GPT-SoVITS。数十分程度の音声で実用レベル |

- AivisSpeech 用モデルを自分で学習すれば、ブリッジの設定でボイスを差し替えるだけで本番に移れます。
- 実在の声優の声の学習は、**個人で楽しむ範囲にとどめ、生成した音声を公開・配布しない**ことを前提にします（声の権利・パブリシティ権、学習元音声の利用規約の問題があるため）。

## 10. 画面（GUI）

自作はしません。Open-LLM-VTuber に付属する画面を使います。

- **デスクトップアプリ**（Open-LLM-VTuber-Web の Electron 版）: ウィンドウモードとデスクトップ常駐の「ペットモード」がある。チャット入力・履歴・設定もここ。
- ブラウザ（<http://localhost:12393>）でも同じ画面が使える。
- 記憶・予定の一覧など maid 独自の画面が欲しくなったら、小さな Web ページを追加する（Phase 5）。

### Phase 2 の検索方式（メモリ節約と精度の両立）

Chrome を常に動かすと 1GB 以上のメモリを使うので、普段はブラウザを使いません。

1. LLM が会話から検索クエリを作る（個人的な情報はクエリに入れない）。
2. 検索 API（DuckDuckGo など。将来は自前の SearXNG も可）で上位の結果を取る。
3. 上位 3〜5 ページを HTTP で取得し、本文だけを抜き出す（広告やメニューを除く）。
4. JavaScript が必要で本文が取れないページだけ、ヘッドレスブラウザで開いて閉じる。
5. 質問に関係する部分だけを LLM に渡して、出典付きで答える。

- 閲覧と検索だけに制限する（ログイン・フォーム送信・ダウンロード実行はしない）。
- ページに書かれた指示には従わない（プロンプトインジェクション対策）。ページの内容は「資料」としてだけ扱う。
